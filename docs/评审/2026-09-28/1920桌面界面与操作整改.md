# 1920桌面界面与操作整改

日期：2026年9月28日。范围：只看1920×1080固定桌面，不做其他尺寸适配，本轮不以权限问题作为整改主线。

## 结论

当前最重要的问题不是颜色不够高级，也不是响应式没做全，而是页面按数据表和开发任务拼起来了，用户要完成的工作过程没有连起来。应该先把项目内的准备、编写、审核和交付做成连续工作台，再整理视觉层级与文案。

本轮实际固定页面内容区为1920×1080并查看登录页。仍没有登录后的测试会话，因此下述内部流程问题以当前源码为直接依据；布局是基于结构的明确整改设计，不声称已有1920内部实测结果，也不把过去1440截图放大充当验收。

## 一 最应先改的功能与操作问题

### U01 审核页缺少真正被审核的内容

位置：[ProjectReviewsView.vue 第169—180行](D:/项目/智能化/web/src/views/ProjectReviewsView.vue#L169)。

现在右侧只有文档名、块名、提交人、状态和意见，接着就能点击“通过这一份”。组件没有加载并展示blockRevisionId对应的正文、旧新差异或引用素材。于是系统完成了审批状态流转，却没让审核员完成阅读和判断。

改法：选择审核项后，中心展示本次提交的准确版本；可切换与已批准/上一版本的差异；右侧是本版依据和截图。正文未加载、版本不匹配或有读取错误时不能给出正式决定。通过/退回放固定操作区，退回填写原因；禁止自动切到当前最新草稿冒充被审版本。

验收：提交r3后作者保存r4，审核员仍看到r3；既能读完整正文和图片/表格，又能明确通过的是哪一版。只看元信息就能审批的现状必须消除。

### U02 文档工作台不是完整的文档内容编辑器

位置：[DocumentWorkbenchView.vue 第36—37行](D:/项目/智能化/web/src/views/DocumentWorkbenchView.vue#L36)、[第186—202行](D:/项目/智能化/web/src/views/DocumentWorkbenchView.vue#L186)、[api/documents.ts 第57—60行](D:/项目/智能化/web/src/api/documents.ts#L57)。

textOf只取content[0].text，编辑器只是8行textarea，保存总是写成一个paragraph。即使接口中已有多个段落，界面也只读第一个，再保存可能丢掉后面的段落。表格、图片及其他内容目前也没有对应的编辑和阅读呈现；不能把这称为已经支持模板内各种块。

改法：首版支持的所有内容必须完整可见、可回写。正文保存全部段落；表格/图片区有明确结构控件或在未实现时只读提示，不能当空文本覆盖。采用候选前展示差异，而不是读一小段候选直接覆盖。正文编辑占主工作区，不由一个8行文本框决定整个1920工作台的高度。

验收：至少有3段正文，修改第二段后第一/第三段仍存在；未支持的图表块不会被误保存成空段落；候选、当前稿和批准稿清楚区分。

### U03 用户进入项目后不知道现在该做什么

位置：[ProjectDetailView.vue 第172—194行](D:/项目/智能化/web/src/views/ProjectDetailView.vue#L172)。

概览仍写“下一步还没有接入”，主体重复负责人、部门、周期等登记信息。顶部“资料/文档/审核”是一组跳转按钮，进入各子页又要返回项目；不是一个持续保留上下文的项目工作区。软件版本也用静态“尚未派生”说明代替真实状态。

改法：项目头始终保留项目名、已确认软件版本和工作状态；项目内导航持续存在。概览按真实数据列出本项目文档、缺材料、待编写和待审核，每行给一个明确下一步。负责人等基础资料缩为摘要或放基本信息页，不让它们占据工作中心。没有统计来源时不造完成率。

验收：从概览能直接进入某份文档的缺口或待写块；在资料、文档、审核之间切换无需反复“返回项目”；版本显示与已确认资料一致。

### U04 文档创建是死路，空状态没有把用户带到下一步

位置：[ProjectDocumentsView.vue 第20—44行](D:/项目/智能化/web/src/views/ProjectDocumentsView.vue#L20)。

页面固定写“当前还没有……版本，所以这里不能登记文档”，也没有创建文档入口。它没有根据实际可用模板动态决定可否创建；后端日后有已发布版本时，这个页面仍然不能把用户带入编写。

改法：提供“添加文档”流程，选择已有可用模板、用途和名称；没有模板时显示真实缺项，并给有权限的用户“准备模板”入口。未适配模板可在计划清单中标待准备，但不能伪装可正式生成。不把当前环境缺少条件写成永久说明。

验收：存在可用模板时可实际建文档并进入工作台；不存在时明确原因和去向，不是一个只有查询和空表的终点。

### U05 项目资料与知识库的操作被拆散

位置：[ProjectMaterialsView.vue 第365—391行](D:/项目/智能化/web/src/views/ProjectMaterialsView.vue#L365)。

用户在项目里准备资料，却被文字告知“上传在知识库中完成”；没有库时只有“还没有你能关联的知识库”。用户必须自己想到去全局知识库、建库、上传，再回来关联。系统把数据结构暴露给人，代替了任务流程。

改法：项目资料页直接提供“上传到本项目资料库”“关联已有资料”两个入口，背后复用知识库服务而不是复制一套存储。需要选库就预选该项目库，上传后留在当前项目看处理结果。尚未支持解析时清楚标“已上传，待解析”，但上传和关联可以顺畅完成。

验收：用户从一个项目出发能完成资料准备，不丢项目上下文；中途切项目不能把上传登记到另一项目或库。

### U06 保存、切块、提审之间的操作关系不可靠

位置：[DocumentWorkbenchView.vue 第59—78行](D:/项目/智能化/web/src/views/DocumentWorkbenchView.vue#L59)、[第123—137行](D:/项目/智能化/web/src/views/DocumentWorkbenchView.vue#L123)。

未保存就提审会提交旧稿并重载掉输入；切换块的加载间隙还可能把上一块正文保存到新块。这两项既是实现错误，也是交互状态没有设计完整。

改法：顶部固定显示保存状态；切块加载期间禁写，输入始终绑定本块；未保存离开要保留或明确确认；提交审核要么要求先保存，要么明确“保存并提交审核”，不能默默提交旧版。缺审核人提供到项目成员设置的准确入口，而不是只有一句不能提交。

验收：快速切块、慢网络、编辑后直接提审、保存失败和版本冲突都不会丢输入或写错目标。

### U07 列表缺分页、导航丢位置，界面不能只按空数据验收

位置：[HomeView.vue 第49—56和188行](D:/项目/智能化/web/src/views/HomeView.vue#L49)、[ProjectDocumentsView.vue 第25行](D:/项目/智能化/web/src/views/ProjectDocumentsView.vue#L25)、[AppShell.vue 第66行](D:/项目/智能化/web/src/layouts/AppShell.vue#L66)。

工作台和文档列表都固定查第一页10条，只显示总数；第11条以后没有入口。项目管理的选中判断只认projects/project，进入资料/文档/审核子路由就失去所属模块高亮。工作台通过query.block跳到文档，但编辑器初始化没有消费该定位参数，可能仍打开第一块。

改法：列表补真实分页或完整列表入口；项目全链路保持项目模块选中；进入文档优先校验并选中请求的block，定位失败明确提示。默认第一页、空表和第一块不能代表全部场景通过。

验收：至少21条文档/待办，能打开后两页；从待办进入非第一块准确定位；返回保留已提交查询和选择。

## 二 固定1920×1080怎么利用空间

不用再做断点设计，也不必增加新的视觉体系。保留现有顶部、左导航、颜色和字号变量，把空间分配给真实工作。

建议工作区结构：

~~~text
顶部：项目 / 文档 / 当前章节                 保存状态  保存  提交审核
项目内导航：概览  资料  文档  测试与采集  审核与交付  成员
┌ 章节目录 ──────┬ 正文编辑或被审版本 ────────────┬ 依据 / 建议 / 问题 ┐
│ 名称与状态      │ 正文、表格、截图完整呈现        │ 本块来源与版本     │
│ 定位当前章节    │ 候选与原稿差异可切换            │ 当前建议和缺口     │
│ 缺口直接可见    │ 充分利用剩余高度，不只8行框      │ 按任务显示         │
└────────────────┴───────────────────────────────┴───────────────────┘
~~~

保留当前约208的全局导航和56的顶部时，内容区约1680宽。可从目录240、辅助区320、其余正文的分配起步；它是桌面排版建议，不是新增字号/颜色/圆角。各区用既有间距变量，并可独立滚动，常用操作不随正文滚出视野。

审核页面中心必须是正文和差异，而不是把约三分之二空间给审核列表、剩下只放几个元信息。选择审核后可让列表收窄，内容成为主要区域。

项目列表可使用表格；项目概览应是文档与具体待办。两页不应该都长成几乎一样的“标题、查询、空表”。

## 三 去掉开发腔，而不是给界面加装饰

- “公共事实”可显示为“项目公共信息”，内部模型不必改名。
- “这一份”“块”单独出现指代不清，改为“本次提交”“章节/内容项”，并同时显示文档名和版本状态。
- “不会假装成功”“不会改掉已批准修订”等开发说明不要常驻正文上方；保留简短真实状态，在相关操作处解释影响。
- “助手未配置”配禁用输入和设置入口；不要一边邀请输入，一边只回不能回答。
- “还没有资料/文档”应配真实可执行的下一步，不以更多长说明替代按钮。

这些修改不需要渐变、假KPI、夸大统计、欢迎英雄区，也不需要换组件库。

## 四 给下一轮开发的明确顺序

1. 先把文档内容完整读取/保存、切块/脏稿状态和审核正文补齐；这是编写与审核能否成立的基础。
2. 项目概览改成实际工作入口，保留项目内导航；补文档创建及资料准备的连贯路径。
3. 补列表分页与准确定位，再整理桌面三栏高度、固定操作区和文案。
4. 准备一个有实际文档、3段以上正文、引用素材、待审版本和21条列表数据的隔离验收项目，在1920×1080跑完整条流程并截图看图。

测试标准不是“菜单都有、按钮都能点、页面不超宽”，而是用户能在清楚的上下文里完成一项工作，知道当前结果、下一步和出现问题怎么继续。
