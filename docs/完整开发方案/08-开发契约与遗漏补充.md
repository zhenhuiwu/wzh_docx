## 二 AI 候选内容怎么保存和采用

将三个概念明确区分：

1. 候选修订：Agent生成并校验后持久化的提案，不自动替换编辑器当前正文。
2. 当前工作稿：用户当前编辑和准备提审的版本，可以来自人工录入或明确采用的候选。
3. 已批准版本：审核人针对具体修订批准的内容，后续工作稿不能原地覆盖它。

可以沿用已有 block_revisions 模型，增加来源标记及当前稿/批准稿引用，不需要重建通用分支系统。

示例行为：当前工作稿为r3；Agent基于r3及固定来源生成候选c1；此时界面应显示“候选已生成，尚未采用”，当前稿仍是r3。用户查看差异并采用时，检查当前稿仍为r3、来源版本仍适用，成功后切换当前稿并记录采用者。若人工已编辑为r4，返回版本冲突，保留c1与r4供比较，不能默认覆盖。

部分采用或人工修改候选时形成新修订，并保留其来源与决定；候选原始内容不被悄悄改写。拒绝候选不删除原有正文。再次生成创建另一候选，不撤销以前的批准记录。

候选生成成功、采用成功、草稿保存、审核通过和正式导出是五个不同结果。消息区、任务卡和文档目录必须使用同一个业务状态来源，不能一个显示完成、另一个仍偷偷覆盖。

建议新增或冻结的接口行为：GET块修订列表可区分候选与当前稿；POST /blocks/{id}/revisions/{revisionId}/adopt 带 expectedRevision 执行显式采用；拒绝候选只更新候选处置记录。它们属于建议接口，未在仓库实现。批准仍只针对当前选定的具体修订。

## 三 统一任务状态与 API 口径

### 3.1 任务值建议

服务端枚举、前端类型和显示文案从同一合同维护，不能每个页面自己把“完成”翻译成不同含义。

| API值 | 用户文案 | 可接受动作及约束 |
|---|---|---|
| queued | 排队中 | 可请求取消；领取前再次鉴权 |
| running | 执行中 | 可请求暂停/取消，但不能立刻宣称外部动作已停 |
| waiting_input | 等待补充 | 补齐指定输入并重验来源/权限后继续；可以取消 |
| pause_requested | 暂停中 | 等执行器到安全边界，未停稳不开放接管 |
| paused | 已暂停 | 明确无未核实动作后，可继续或取消 |
| cancel_requested | 取消中 | 尚未完成停止/必要核实或清理，不显示已取消 |
| needs_verification | 结果待核实 | 只允许核实/受控人工处理；不盲目重放提交动作 |
| succeeded | 已完成 | 本任务固定范围处理完；不表示所有测试通过或文档已审核 |
| failed | 执行失败 | 保留错误与候选，显式重试形成尝试记录或新关联任务 |
| cancelled | 已取消 | 已停止后续步骤；历史结果保留，已发生副作用不会被声称撤销 |

结果待核实优先于简单的暂停或取消终态；必要时另存用户的停止意图，核实后再完成停止。已经发到外部系统的动作可能无法立即取消，界面不能为满足按钮反馈而提前显示成功。

批量文档任务的目标清单启动时固定。部分块完成、部分缺材料时，父任务显示等待输入及各子项结果；有可继续的子项时可继续处理。不能删除失败/阻塞项来把父任务改为全完成。失败未解决时显示失败或等待处理的明确汇总，不用100%进度掩盖。测试用例的断言失败是业务结果，收集并报告该结果的任务仍可能成功。

### 3.2 联调合同必须补齐的字段

已有架构文件给了端点和请求示意；真正联调前还需冻结每个实际实现端点的字段类型、必填/可空、长度、默认值、枚举、输入输出来源和失败码。后端实际schema是合同来源，前端不能另维护互相矛盾的字段定义。

建议JSON继续使用现有示例的camelCase；数据表命名不必相同，但转换应集中且有测试。PATCH省略字段表示不修改；显式null只能用于允许清空的字段；空字符串不自动等同于null。时间保留时区，列表排序要有稳定的内部次级键；内部ID仍不在UI展示。

| 稳定错误码建议 | 场景 | 界面应做什么 |
|---|---|---|
| AUTH_REQUIRED | 未登录或会话失效 | 进入认证流程，避免把敏感未保存内容写到普通本地缓存 |
| FORBIDDEN | 无当前操作或对象权限 | 不显示敏感详情，不能无限重试 |
| REVISION_CONFLICT | 内容或来源版本已变 | 保留候选/输入，提供比较，不覆盖 |
| PRECONDITION_MISSING | 缺材料/模板/环境 | 定位需要补齐的具体项 |
| INVALID_TRANSITION | 当前状态不允许动作 | 刷新真实状态，解释不能操作的原因 |
| IDEMPOTENCY_CONFLICT | 同幂等键却请求内容不同 | 不重复执行，核对原请求 |
| LIMIT_EXCEEDED | 文件、调用、步骤或资源超限 | 显示实际限制及可行处理方式 |
| DEPENDENCY_UNAVAILABLE | 模型/解析/工具暂不可用 | 明确等待或失败，不用空结果冒充成功 |

HTTP状态继续沿用架构方案，新增错误码不是允许自由改返回结构。成功/错误中的 requestId 用于排查，不作为模板或文档显示编号。

事件流明确 sequence、type、目标、状态及候选引用；事件重放去重，断线时保留任务，过期游标则重新获取状态快照再订阅。进度事件不能当作最终采用或批准结果。

## 四 权限叠加与资料衍生内容

推荐默认策略：一次请求需要同时满足有效身份、当前操作能力、目标项目/库的可见范围、对象状态、相应来源权限；工具动作还需目标环境与动作范围授权。没有明确授权就拒绝，不能因为多个角色叠加就把资源范围扩成全公司。

全局平台管理员管理账号/配置，不默认读取所有项目资料；项目负责人不是所有知识库管理员；审核权限不自动给测试执行权；浏览器凭据可用不代表用户可操作任何业务页面。首版可以通过有限角色与范围校验实现，不建设通用策略语言。

来源转成摘要、聊天回答或文档内容后，仍可能包含受限信息。默认生成结果不能被分享给比来源授权范围更广的人；需要复制/脱敏发布为项目共享材料时必须有明确许可与记录。批准版本与内部归档是否具有独立保留/查看权限，必须纳入D09和保留政策确认，不能以“已经生成过”绕过撤权。

权限收紧后需同时检查后续检索、旧消息、当前稿、导出和文件预览，必要时标记复核/限制访问。不能只把引用链接隐藏而继续返回原敏感正文。事件流和缓存使用相同作用域。

## 五 固定验收样例包而不是临时挑成功案例

在S0建立样例目录和清单即可，当前没有收到足够真实材料，不创建空文件伪装成完成的样例。建议未来保存到 D:/项目/智能化/tests/fixtures/acceptance，并在清单中注明是否实际存在、来源授权与适用范围；该目录是计划位置，不是本次已生成的测试工程。

| 样例类 | 应有内容与判定依据 |
|---|---|
| 项目和权限 | 两个隔离项目、不同角色、公开/受限材料；允许和拒绝结果由负责人确认 |
| 知识检索 | 可回答、无依据、矛盾、中文长表和扫描件等；问题对应的正确来源和不应可见材料 |
| 文档块 | 输入事实、资料、当前稿、候选、批准内容、缺材料与冲突场景 |
| 单元测试 | 批准语言的代码快照、函数范围、预期依据、应通过/失败/无法构建的情况 |
| 浏览器 | 指定环境/角色/数据、操作、断言、清理、提交结果未知与接管场景 |
| Word | 原模板、合法合格样例、短文/长文/多图/重复表数据、每项格式判据 |
| UI | 受影响路由、状态和数据、375/768/1440截图及1280补查；核对的版本信息 |

格式判据必须具体到适用位置、规则值、来源与检查方式，例如正文/标题的字体字号、段落间距、表格跨页、页眉页脚。数值应来自公司已确认规范或认可样例，不从“438C”文件名推测，也不把原模板所有现有样式未经审查就当标准。

每个样例登记名称、用途、输入版本/哈希、预期结果、判定人和更新时间；黄金样例必须是独立确认的参考，不能把待测模型本次输出直接设为正确答案。调整验收预期须记录原因，不能为通过而改低门槛。

## 六 采集和测试覆盖清单

开始自动执行前固定本任务覆盖范围：

- 单元测试：代码版本、包含/排除文件、目标函数/重载、需求或接口依据、选择的用例。
- 功能测试：需求或功能、角色、前置数据、步骤、预期检查、所需证据、清理及允许副作用。
- 手册采集：用户角色、用户要完成的任务、入口/步骤、关键截图、相关说明块，以及需要外部资料的安装/恢复等内容。

每项有实际状态、结果与证据，排除项有原因和批准。分母是已批准范围，不是恰好发现了多少函数或截了多少图。任务过程中发现新功能可以建议增加，不能静默扩大工具权限或声称未选范围也已覆盖。

“范围内已处理”“实际执行通过”“手册素材齐备”和“文档已审批”分别统计。测试失败、未执行和人工判断项不能被当作不存在。界面只显示名称、用途和清楚的状态，不暴露模板/文档内部标识。

## 七 界面设计与开发产物的边界

目前已有文字说明和结构线框，没有逐页高保真设计图，也没有真实修改后的截图验收。后续不必另造一套庞大设计系统；先在现有Vue3和令牌内实现一个明确的纵向小任务，在四种宽度与关键状态上核对，再复用通过的业务模式。

界面交付证据应绑定源码版本/快照、配置、接口或测试夹具版本、页面/角色/数据状态、视口、操作步骤、截图位置与实际看图结论。后续代码或数据变化导致画面变化时，旧截图不能继续作为当前版本已通过的依据。夹具截图不能证明真实接口联调。

实际OpenAPI/类型、数据库迁移、运行环境锁定、自动化测试脚本、可运行Skill包和合格Word文件都属于开发交付物，当前的文档设计不能冒充这些产物。已有设计足以指导它们，但不能在未实现时给出“全部准备完成”的结论。

## 八 补充验收场景

下列B01—B08补充原A01—A48，不改原编号，也不假称已经执行。

| 补充项 | 操作 | 必须结果 |
|---|---|---|
| B01 候选采用 | 当前r3生成候选期间人工改r4，再采用候选 | 产生冲突，r4不被覆盖；候选可比较，批准版不动 |
| B02 暂停取消 | 外部提交未返回时请求取消 | 不立即显示已取消；进入核实并保留停止意图，禁止重放 |
| B03 批量范围 | 部分目标缺材料或执行失败 | 父任务明确部分结果和阻塞，不缩分母宣称全部完成 |
| B04 复合权限 | 平台管理员、项目审核者访问无权材料/工具 | 角色不能越过项目/库/工具范围，衍生文本不泄漏 |
| B05 联调一致 | 按实际schema发送缺字段、null、错误枚举和过期修订 | 前后端处理一致，稳定错误码和恢复入口明确 |
| B06 证据版本 | 用旧源码截图或本次模型输出当黄金参考 | 不作为当前验收通过证据；要求正确版本和独立预期 |
| B07 覆盖统计 | 只执行选定范围一部分或发现新函数 | 显示真实分母/排除理由，新增范围需明确授权 |
| B08 交接输入 | 接手环境缺文件、运行工具或正式批准记录 | 报明确缺口，不伪造实现、截图、决策或运行能力 |

涉及政策的范围必须先由用户确认，涉及技术合同由实现方落到真实schema并验证。本补充是查漏后的建议约定，不是已实现或已批准的数据库迁移。
