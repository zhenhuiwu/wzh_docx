# 项目文档智能编制系统开发设计总览

版本：v0.1 评审稿

依据：本次需求讨论、工作目录中的 20 份模板及官方技术资料。

## 1 结论

这不是“聊天后下载 Word”的软件，而是一个项目级文档工作台：共享已确认资料，按固定模板和专属 Skill 组织内容，由同一个 Agent 分多轮完成小任务，必要时调用函数测试或浏览器工具获取真实证据，再通过程序排版、检查、审核和交付。

需求方向可行，但本地模型能力、代码环境、浏览器可操作范围及严格 Word 输出链尚未验证。现在可以开始 G0 小范围验证，不宜直接承诺全套模板、任意代码或任意界面的一键全自动生成。

本次只创建 Markdown 设计说明和 JSON 检查附件。未编写业务代码，未修改原始 Word 模板，未调用公司模型，未执行被测代码，未操作公司业务界面，未部署系统。

## 3 建议冻结的核心原则

1. 一个项目管理一组实际文档，不是每份模板只能有一个文档。
2. 每份文档绑定版本化模板包，模板包包含 Skill、字段规则和块级提示词。
3. 同一个 Agent 持续工作，每轮只处理一个明确任务；用户不必不断手动发送“继续”。
4. 共享的是项目范围内的事实、来源、已确认结果和进度，而非一条无限增长的聊天记录。
5. 事实直填，AI 只编写必要描述；草稿不能未经确认升级为权威事实。
6. 单元测试、功能测试、手册采集先取得实际记录，再编写文档。重写文字不等于重新执行。
7. 程序限制写入范围、工具权限与导出结构，Skill 本身不构成安全或正确性保证。
8. 人工修改与已批准版本受保护；上游变更触发定位复核，不静默重写所有文档。
9. 截图是证据或教学素材，不自动等同于测试通过；正式报告也可以如实报告失败。
10. 正式交付锁定文档、内容、事实、模板和证据版本，历史交付不受后续改动影响。

## 4 从实际模板发现的三个关键问题

第一，现有 20 份 DOCX 不是已配置好字段和重复区的机器模板。主文档 XML 未检出内容控件，且有多分节、表格、目录域和指导文字；仍需提炼和验收，而不是直接上传就能稳定生成。

第二，文件清单没有单独命名的单元测试或功能测试文档。应确认这两个场景分别对应哪些 STP、STD、STR 实例或公司专用模板，不能混淆测试类型与文档类型。

第三，SUM 用户手册含安装设置、备份、恢复等非截图内容，需要运维或产品资料。AI 操作界面主要解决操作规程与截图采集，不能推断未验证的运行和恢复能力。

## 6 推荐首版架构

没有既有公司技术约束时，候选为 Vue 3 与 TypeScript、Python 与 FastAPI、PostgreSQL、内网文件存储、Playwright 以及 docxtpl。优先复用团队熟悉的基础技术，具体版本和离线依赖在 G0 后锁定。

先用一个应用、一个受控 Agent 执行器和数据库任务队列；代码测试、浏览器与渲染采用必要的隔离工作进程。首版不建设多 Agent 平台、通用流程编排器、完整在线 Word 编辑器或独立知识图谱平台。

## 7 开工前优先补齐的信息

1. 本地模型名称或版本、接口调用方式、上下文与工具调用能力。
2. 主体代码语言、现有测试框架、构建和依赖环境。
3. 被测前端的形态、浏览器、登录方式及可用测试账号。
4. 公司验收使用的 Word/WPS 版本、字体和已认可成品样例。
5. 单元测试与功能测试分别需要哪些正式文档。
6. 执行环境和网络边界、演示数据、允许的副作用操作。

完整的 10 项待确认决策见需求说明。缺少上述信息不影响继续评审界面和数据模型，但不应直接开放自动测试、承诺格式百分之百一致或确定完整工期。

## 8 最小真实验证闭环

选择一个实际项目、一份代表性模板和一个有真实材料的内容块，验证“确认资料 → Agent 多轮处理 → 范围与来源检查 → 人工审阅 → 程序填充 → 目标办公环境验收”。再分别接入一个函数测试与一个浏览器任务，证明执行记录能回到对应文档。

这个闭环是为了验证架构假设，不是把其他已确认需求取消。达到 G0 出口后再按 G1 到 G4 展开开发，逐份适配模板。最终以总人工耗时、事实错误、格式返工和交付质量衡量效果，而不是以生成篇幅或调用次数衡量。
